# Repository Working Rules

These rules apply to all work performed in this repository. They override default
development habits unless explicitly overridden by the repository owner.

## Attribution

Do not include any AI attribution anywhere. Never add:

- "Co-Authored-By"
- "Generated with"
- "Generated by"
- references to Claude
- references to Anthropic
- references to ChatGPT
- references to OpenAI
- model names
- model identifiers
- comments stating or implying that code was AI-generated
- documentation stating or implying that content was AI-generated
- issue text stating or implying that work was AI-generated
- commit messages stating or implying that work was AI-generated

Anything committed or pushed to the repository should look like normal engineering work.

## Agents and Workflows

Do not spawn agents or workflows unless explicitly instructed to do so.

This includes:

- subagents and background agents
- multi-agent orchestration or fan-out
- workflow scripts
- delegating work to a separate agent session

Do the work directly in the current session. If a task appears large enough to warrant
delegation, say so and wait for an explicit instruction.

## Plugins and skills

The installed custom plugins and skills are part of this repository's engineering
environment. Use relevant ones proactively for substantial work rather than recreating
equivalent workflows manually. Select them deliberately based on the task, verify their
conclusions against repository evidence and authoritative sources, and never invoke
plugins merely to create activity. Important findings discovered through a plugin must be
fixed in scope or recorded according to the repository's issue discipline.

## Branch Policy

Work directly on `main`.

Do not create:

- feature branches
- development branches
- temporary branches
- release branches
- pull requests

unless explicitly asked to do so.

At the beginning of work, verify the current branch:

```bash
git branch --show-current
```

If the repository is not currently on `main`, do not silently create or switch branches
in a way that could destroy or overwrite work. Inspect the repository state first.

## Existing Work

Before changing anything:

1. inspect `git status`
2. inspect the current branch
3. inspect recent commits
4. inspect the repository structure
5. inspect relevant documentation
6. inspect relevant open issues when GitHub access is available
7. understand the existing implementation before modifying it

Do not overwrite, revert, discard, or rewrite unrelated existing work.
Do not assume uncommitted changes are yours.
Treat existing uncommitted work as potentially important.

## Scope Discipline

Implement the requested task completely, but avoid unrelated refactoring.

Do not rewrite working code purely out of style preference.
Do not make large architectural changes unless they are necessary for the requested task
or clearly justified.

Prefer the smallest coherent change that correctly solves the problem. If surrounding code
must change to implement the task safely or correctly, make those changes as part of the
same coherent work unit.

## Engineering Quality

Treat the repository as production software unless the project explicitly states otherwise.

Optimize for:

1. correctness
2. security
3. maintainability
4. simplicity
5. reliability
6. testability
7. performance where relevant

Do not trade correctness or security for convenience.
Avoid unnecessary abstractions.
Avoid unnecessary dependencies.
Do not introduce speculative infrastructure for hypothetical future requirements unless it
materially improves the current design.

## Security

Treat external input as untrusted. Validate data at appropriate trust boundaries.

Do not:

- expose credentials
- expose tokens
- expose API keys
- expose private keys
- expose cryptographic secrets
- commit secrets
- log sensitive data unnecessarily
- disable security controls merely to make tests pass
- suppress meaningful security errors without justification

Use established cryptographic libraries rather than implementing cryptographic primitives
from scratch.

Fail securely when authentication, authorization, integrity validation, or cryptographic
verification fails.

When changing security-sensitive code, review the change specifically for abuse cases and
failure modes before committing.

## Dependency Discipline

Before adding a new dependency, determine whether the functionality can reasonably be
implemented using existing dependencies or the standard library.

When a new dependency is warranted, consider:

- maintenance status
- security history
- license
- project activity
- platform support
- runtime or language compatibility
- transitive dependency cost
- whether it is appropriate for production use

Do not add dependencies simply because they make a small task easier.

## Error Handling

Handle recoverable failures explicitly.

Do not allow malformed or attacker-controlled input to crash long-running processes.
Do not silently ignore meaningful errors.

Errors should provide useful diagnostic information without exposing sensitive data.
Do not convert failures into apparent success merely to satisfy tests.

## Tests

Changes should include appropriate tests when the behavior is testable.

At minimum, consider:

- expected behavior
- boundary conditions
- malformed input
- failure paths
- regression cases
- security-relevant negative cases

Do not delete or weaken meaningful tests merely to make a change pass.
If an existing test is incorrect, fix it and document why through the code, commit, or
issue where appropriate.

## Local Validation

Remote CI may not be available or authoritative. The local validation suite is the primary
gate.

Before committing finished work, determine the repository's actual validation workflow from:

- project documentation
- build files
- package configuration
- scripts
- Makefiles
- task runners
- existing CI configuration

Run all applicable local checks. This normally includes:

- formatting
- linting
- static analysis
- compilation or build validation
- unit tests
- integration tests
- dependency vulnerability checks
- repository-specific validation scripts

If the repository contains multiple languages or components, validate each affected
component.

Never knowingly commit or push code that fails the applicable local gate.

If a validation step cannot run because of the local environment, clearly distinguish an
environment failure from a software failure.

Do not claim a test passed if it was not run.

## No Em Dashes

The Unicode em dash character, U+2014, is prohibited from anything added to the repository.

Do not use it in:

- source code
- comments
- documentation
- Markdown
- issue titles
- issue bodies
- commit messages
- configuration
- examples
- test fixtures
- generated files intended for commit

Use commas, colons, semicolons, parentheses, or normal hyphens instead.

Before every commit, scan tracked content:

```bash
git grep -n $'\u2014'
```

Also inspect relevant untracked files that are about to be committed. The final repository
changes must contain no em dash characters.

## Issue Discipline

Anything meaningful discovered during development must be handled intentionally.

If you discover:

- a bug
- security concern
- technical debt
- missing test
- missing validation
- unsupported behavior
- documentation gap
- architectural limitation
- dependency concern
- performance problem
- portability issue
- usability problem
- future enhancement
- follow-up work that should not be included in the current task

either:

1. fix it as part of the current work, or
2. create a GitHub issue

Use `gh issue create` when GitHub CLI access is available and appropriate.

Issues should contain enough information for another engineer to understand the problem and
continue the work. Include as appropriate:

- problem description
- affected component
- reproduction steps
- expected behavior
- actual behavior
- security or operational impact
- likely implementation direction
- relevant files or modules
- acceptance criteria

Do not create vague placeholder issues.
Do not leave discovered problems only in chat output.
Do not use loose TODO comments as substitutes for tracked issues. A TODO comment may
reference an existing issue where useful.

## Documentation

Update documentation whenever the implementation changes behavior that users, operators,
developers, or maintainers need to understand.

Do not document planned functionality as if it already exists.

Clearly distinguish:

- implemented behavior
- experimental behavior
- planned behavior
- known limitations

Examples and commands in documentation should reflect the actual implementation.

## Comments

Comments should explain:

- why something exists
- non-obvious invariants
- security assumptions
- protocol requirements
- unusual implementation constraints

Do not add comments that merely restate obvious code.
Do not add conversational commentary about how the code was produced.

## Commit Discipline

Commits should represent coherent engineering changes.

Before committing:

1. inspect the full diff
2. inspect `git status`
3. verify no unrelated files are staged
4. review the change for correctness
5. review security-sensitive changes for failure modes
6. run applicable tests
7. run the full local gate
8. run the em dash scan
9. verify Git author identity

Commit messages should be concise and describe the engineering change. Examples:

```
Implement connection retry handling
Add validation for configuration input
Fix race in worker shutdown
Add regression tests for parser failure
Harden authentication error handling
Document deployment configuration
```

Do not use AI attribution in commit messages or trailers.
Do not use "Co-Authored-By" attribution for an AI system.

## Push Policy

Finished work must be pushed once it is:

1. implemented
2. reviewed
3. tested
4. locally validated
5. committed

Push completed work to `main`. Do not leave finished commits only on the local machine.
After pushing, verify that the push succeeded.

Do not force-push unless explicitly requested.
Do not rewrite public history unless explicitly requested.

## Destructive Git Operations

Do not use destructive Git operations casually. Do not run commands such as:

```
git reset --hard
git clean -fd
git checkout -- .
git restore .
git push --force
git push --force-with-lease
```

unless the operation is clearly necessary and has been explicitly authorized.

Do not discard changes simply because they are unrelated to the current task.

## Repository Hygiene

Do not commit:

- temporary files
- build artifacts that should be ignored
- editor-specific junk
- debug output
- local environment files
- credentials
- secrets
- unnecessary generated files
- large binaries unless the project intentionally tracks them

Update `.gitignore` when appropriate. Do not make broad `.gitignore` changes that could
accidentally hide important source files.

## Working Method

### Before implementation

1. inspect the repository
2. inspect `git status`
3. confirm the branch
4. inspect recent commits
5. understand the relevant implementation
6. inspect relevant tests
7. inspect relevant issues
8. determine the smallest coherent solution

### During implementation

1. preserve existing behavior unless intentionally changing it
2. keep changes scoped
3. add or update tests
4. validate assumptions against the actual code
5. avoid leaving incomplete work
6. track meaningful deferred findings as issues

### Before commit

1. review the full diff
2. verify no unrelated changes are included
3. run targeted tests
4. run the complete local validation suite
5. run security or dependency checks where applicable
6. run the em dash scan
7. inspect `git status`
8. verify author identity

### Completion

1. commit as MalloyTheDev
2. push to `main`
3. verify the push succeeded
4. ensure meaningful deferred findings have issues
5. ensure the working tree is in the expected state

## Decision Making

Do not ask unnecessary questions.

If a normal implementation detail can be determined from:

- the repository
- existing conventions
- tests
- documentation
- established engineering practice

use sound engineering judgment and proceed.

Ask before making decisions that are difficult to reverse or that materially affect:

- public APIs
- wire protocols
- persistent data formats
- security models
- licensing
- compatibility guarantees
- major architectural boundaries
- destructive migration behavior

When uncertainty does not materially affect the architecture or user-facing contract,
choose a defensible implementation and continue.

## Definition of Done

A task is not complete merely because code was written.

Work is complete when:

- the requested behavior is implemented
- relevant tests exist or were updated
- applicable tests pass
- formatting passes
- linting and static analysis pass where applicable
- dependency or security checks pass where applicable
- repository-specific validation passes
- the diff has been reviewed
- no unintended files are included
- no em dash characters were added
- meaningful deferred findings have issues
- the commit author is MalloyTheDev
- the work is committed
- the finished work is pushed to `main`

Do not report work as complete until these requirements have been satisfied.
